# 项目写作流程

本项目把已有 writing-skill 的受众区分、事实契约、Argon 成文和独立验收落实为可本地运行的流程。先读 `AGENTS.md` 及工作区配置，来源与取舍见 [provenance.md](provenance.md)。

## 从材料到稿件

1. 定读者与交付物。内部笔记让未来的自己能复查判断与证据；公开条目让没看过讨论的读者也能理解和使用。正文篇幅、标题数量与例子由问题决定，短知识条目不自动扩成分析长文。
2. 在私有底稿记录问题、已认领的结论、信息增量、可用事实与来源、示例性质、尚未核实的部分。分析环节必须实际查询 lizheng MCP 并读到原文，将适用的方法、边界与本题的推理分清；没有相关结果则如实记下。MCP 不可用时报告未完成，未经用户明确同意不能用本地快照替代。可用 `brief.md` 和 `source_contract.md`，已有笔记满足同样用途时直接沿用。敏感原文和凭证不能提交公开仓库。
3. 用 Antigravity CLI 的 Argon 起草正文。读 [作者表达约定](author-voice.md)，给 Argon 具体读者、素材与字数需求。保留 JSON 响应以核对模型和实际输出，不把生成结果的解释或计划当成文章。
4. 用 Argon 做文风改写。按需要读取项目内固定文本 `resources/qu-ai-wei/SKILL.md` 及其 references，随后处理阅读负担，再按作者表达约定清理重复、空话和不必要的改写。规则文本提供编辑依据，正文仍由 Argon 生成。无需安装第三方脚本，不调用缺失的 `essay-phase3` 或 voice-lora 服务。lieflat 当前版有额外脚本流程和非商业许可条件，作为可选工具另行评估，不属于本流程依赖。
5. 只修改需要修订的段落，其余逐字保留。编排者可以拼接 Argon 输出、设置 front matter、修正链接目标和格式；改变正文措辞或事实表述也交还 Argon。补 Prompt、练习和解析同样遵守这个分工。

## 核对最终稿

6. 核对每一处经历、数字、归属、比较口径与确定程度。AI 改写不能把推测变成已验证的效果。检查删除的限定、事实与来源是否一起消失；假设例子明确是假设。
7. 使用宿主 fresh-context 子代理独立核事实与冷读。事实审查拿最终稿和来源契约；冷读只拿最终稿和目标读者，不给起草 brief。请普通读者指出卡住或回读的句子，复述要点，并检查作者是否在说教。短稿逐处判断影响，不为凑分数忽略理解障碍。没有独立审查能力时明确列为未完成，不让起草会话冒充冷读。
8. 跑项目配置中的 prose lint，以及本技能内 `resources/fatigue_scan.py`。后者的人读目录在 `resources/fatigue-catalog.md`。逐处判断扫描提示，确认必要引用、清单和术语的用途。误报写清命中的原文与理由，不为正则改坏句子。长文篇幅门槛和链接数不能自动变成短知识条目的硬要求。
9. 有实质问题则把问题和段落交回 Argon，小修后核该段，并让同一位审稿人复评相关位置。通过的检查只对实际审过的最终版本有效。交付记录写真实检查结果与未完成项。

内部笔记可以保留底稿和不确定性，公开文章中的读者不需要知道内部工序。发布交给 `thinking-to-knowledge` 的发布核对；不要在写作技能里自动附带提交或推送授权。
