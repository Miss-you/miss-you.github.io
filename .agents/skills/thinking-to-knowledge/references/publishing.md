# 博客同步与发布

在博客根目录读 `AGENTS.md`、`kb/README.md`、项目 `writing-wiki-from-practice`。构建命令以博客当前版本为准。路径和默认分支从配置与 Git remote 读取。

1. 读取工作树和暂存区，记录已有改动。从远端读取最新目标分支，检查同 slug、同问题的条目。工作树脏或远端并发时可以用独立临时副本，不重置用户目录，不批量暂存。
2. 写入或更新 `content/kb/` 的条目，核对 `lang`、稳定 slug、日期、topic 和 `draft`。本地笔记是保存知识的交付物，博客副本是公开读本，二者路径都需留下记录。
3. 按 CI 先生成依赖模板，再构建。全新检出可能尚无 `layouts/partials/generated/text-compare/assets.html`，先按锁文件安装构建依赖，再运行 `node scripts/build-text-compare.mjs`，不要误判为文章导致 Hugo 出错。
4. 运行知识库维护指南中的必要检查。预览文章和知识库索引；Prompt 能完整复制，选择题逐项显示，`details` 答案默认折叠，来源和锚点可用。输出目录放临时位置，生成物不提交。
5. 只暂存本次文件，检查 diff 和凭证。提交后推送前若 main 已变化，先读取远端再比较同文件。不同内容可正常合并；同条目有并行新增时检查是否已经满足用户请求，不重复叠加。不要强推。
6. 推送成功后等站点部署。仓库的 Hugo deploy 成功之后，可能还有单独的 GitHub Pages build and deployment。最终打开线上条目，核对新增文本、Prompt 和练习，页面缓存未更新时继续检查实际部署状态。
7. 同步到用户指定的本地博客目录前，确认该文件仍等于本轮读取的版本。遇到新编辑要合并或说明，不直接覆盖。独立副本的提交已推送不代表用户原工作树已前进，不谎称原目录干净或已同步 Git 历史。

推送后先等仓库构建发布流程完成。若该流程只更新 gh-pages，还需等 GitHub Pages 的第二层部署完成，再核对公开 URL 的实际正文；前一层成功后看到旧内容不能直接报上线。按提交 SHA 查对应 run，线上核对要包含本次真正改动的文字。

公开提交不得包含 `.mcp.json`、认证日志、作者私密笔记或本机路径配置。没有可用的凭证扫描器时检查本次 diff 的密钥、口令、私钥与 URL 内嵌凭证，并记录扫描方式。
